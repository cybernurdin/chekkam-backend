# Demo Document Verification Kit

A repeatable, fictional-data demo of Chekkam's document trust lifecycle — GENUINE, TAMPERED,
REVOKED, NOT_FOUND — proven through the real signing/verification engine, not a mock.

## Architecture

Reuses the existing engine end to end; nothing new was built to fake a result:

- **Signing**: `signDocumentCore()` (`lib/documents/sign-document.ts`) — the same function every
  other surface (web dashboard, WhatsApp, Telegram) calls. Embeds an invisible verification marker
  into supported formats before hashing (`lib/documents/embed/`), signs with ECDSA P-256.
- **Revocation**: `revokeDocumentCore()` (`lib/documents/revoke.ts`) — the same function
  `POST /api/documents/:id/revoke` uses.
- **Verification**: `verifyByUpload()` / `verifyByIdOrPin()` (`lib/documents/verify.ts`) — the same
  functions the public `/verify` page, QR scans, and every bot use.
- **Storage**: fictional certificates are generated by `generateDemoCertificatePdf()`
  (`lib/documents/demo/certificate-template.ts`) and signed for real. The genuine and revoked
  copies live in `documents.original_file_data` (the same column real signed documents use). The
  tampered and unregistered files — deliberately never signed or registered — live in a small
  standalone `demo_trust_assets` table (migration `0018_demo_trust_assets.sql`), never in
  `documents`.
- **No new storage provider**: everything is a `bytea` column in the existing Postgres/Supabase
  database, matching how real signed originals are already stored — no Azure/S3/etc. introduced.

## Database records created

Institution `Chekkam Demo University` (fixed id `a94910a7-063d-4f8a-9f8c-7a169d71c65c`, type
`university` — the closest existing enum value to "Educational Institution"; no new enum value was
added for a cosmetic label), `verified: true`, `status: active`, domain `demo.chekkam.cm`, contact
`verification@demo.chekkam.cm`.

One demo institution-officer profile + `institution_members` row.

Two rows in `documents` (`demo_trust_genuine`, `demo_trust_revoked` document types — used as the
lookup key so re-running the seed finds them instead of duplicating). Two rows in
`demo_trust_assets` (`tampered`, `unregistered`).

## Storage locations

| File | Where | Served by |
|---|---|---|
| Genuine | `documents.original_file_data` | `GET /api/documents/:id/download-original` |
| Revoked | `documents.original_file_data` | `GET /api/documents/:id/download-original` |
| Tampered | `demo_trust_assets` (`key='tampered'`) | `GET /api/demo-trust/download/tampered` |
| Unregistered | `demo_trust_assets` (`key='unregistered'`) | `GET /api/demo-trust/download/unregistered` |

All four download routes and the summary route (`GET /api/demo-trust`) require an authenticated
admin/analyst/super_admin session — this is a protected demo-management surface, not a public one.

## Key management

The institution's ECDSA P-256 key pair is generated the same way every institution's is
(`generateSigningKeyPair()`, `lib/crypto/sign.ts`). The private key **never** touches the database —
only as the env var `DOCUMENT_SIGNING_KEY_A94910A7_063D_4F8A_9F8C_7A169D71C65C`, PEM-encoded with
literal `\n`. If that env var isn't set when the seed script runs, it generates one on the spot,
prints it once (matching the same one-time-reveal pattern `POST /api/institutions` already uses),
and you must persist it — otherwise the *next* run generates a different key and every demo
document starts reporting Tampered.

## Seed command

```bash
cd chekkam-backend
DEMO_SEED_ENABLED=true npm run seed:demo-trust
```

Disabled by default — refuses to run without `DEMO_SEED_ENABLED=true`. If it detects a production
environment (`RAILWAY_ENVIRONMENT_NAME=production` or `NODE_ENV=production`), it additionally
refuses unless `ALLOW_PRODUCTION_DEMO_SEED=true` is also set, printing a loud warning first.

Fully idempotent — re-running it finds the existing institution/officer/documents/assets and
updates only what's out of sync (e.g. the public key, if the private key ever changes), never
duplicating. Verified live across 3 consecutive runs against the real dev database: institution
rows, officer auth users, `institution_members` rows, both `documents` rows, and both
`demo_trust_assets` rows all stayed at exactly 1 each.

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `DEMO_SEED_ENABLED` | Yes, `=true` | Disables the script by default |
| `ALLOW_PRODUCTION_DEMO_SEED` | Only in production | Extra confirmation to seed a live environment |
| `DOCUMENT_SIGNING_KEY_A94910A7_063D_4F8A_9F8C_7A169D71C65C` | Auto-generated if missing | The demo institution's private key |
| `DEMO_TRUST_OFFICER_EMAIL` / `DEMO_TRUST_OFFICER_PASSWORD` | No — defaults provided | Override the demo officer login |

## Demo login

Dashboard (`/login`): `demo-officer@demo.chekkam.cm` / `ChekkamDemoTrust123!` (or your
`DEMO_TRUST_OFFICER_*` override) — role `institution_officer`, member of Chekkam Demo University.

## Verification IDs

Generated fresh per environment by the real ID generator (`CHK-XXXX-XXXX`) — there are no fixed
IDs to hardcode here. After seeding, run:

```bash
curl -s -H "Authorization: Bearer <admin/analyst session token>" https://<host>/api/demo-trust
```

which returns the genuine/revoked verification IDs, their public verify URLs, and download URLs
for all four files. The dashboard **Demo Trust Kit** page (`/dashboard/demo-trust`) shows the same
thing with download buttons and a link to each public verify page.

## Public verification URLs

`https://<host>/verify/<verification_id>` — printed by the seed script and shown on the dashboard
page for the genuine and revoked documents (the tampered and unregistered files have no valid ID of
their own to look up by design).

## How to reset the demo

Re-running `npm run seed:demo-trust` is safe and idempotent, but it does not *delete* anything. To
fully reset: manually delete the two `documents` rows (`document_type` in
`('demo_trust_genuine','demo_trust_revoked')` for the demo institution) and the two
`demo_trust_assets` rows, then re-run the seed script.

## How to demonstrate each result (two minutes)

1. Open `/dashboard/demo-trust`, download **Genuine**. Upload it at `/verify` → **Genuine**, correct
   issuer shown.
2. Download **Tampered**. Upload it → **Tampered** — cryptographic fingerprint mismatch, same
   issuer/verification ID as the genuine one (it still refers to the same ID, printed on the
   certificate; the hash no longer matches).
3. Download **Revoked**, or just visit its public verify URL → **Revoked**, with the stated reason
   — even though its signature is still cryptographically valid, revocation takes precedence.
4. Upload **Unregistered** → **Not found** — never presented as "fake," since Chekkam has no record
   of it either way.

## Troubleshooting

- **Every demo document suddenly reports Tampered**: the signing key env var changed since the
  documents were signed (e.g. seed ran once, generated a key, the process restarted without that
  key persisted, then seed ran again and generated a *different* key). Re-seed after persisting the
  printed key, or accept that the two documents were signed under different key material and treat
  the earlier run's data as the source of truth for that environment.
- **`GET /api/demo-trust` returns 403**: the session role must be `admin`, `super_admin`, or
  `analyst` — not `institution_officer` (this surface is for demo administrators, not the demo
  institution's own officer account, even though that officer exists and can sign real-looking
  documents through the normal dashboard).
- **Seed script exits immediately with no output**: `DEMO_SEED_ENABLED` isn't set to exactly `true`.

## Security limitations

- The demo institution's private key, once generated, exists in whatever `.env`/environment
  variable store you put it in — treat it with the same care as any real institution's key (never
  commit it, never log it).
- `demo_trust_assets` and the demo `documents` rows are real database rows in whatever environment
  you seed — running this against production creates real, visible (though clearly fictional-data)
  records, which is exactly why the production gate exists.
- The tampered/unregistered download routes are IP-rate-limited the same as every other
  `/api/documents/*` route, but are not otherwise access-controlled beyond the admin/analyst role
  check — this is a demo-management tool, not a citizen-facing feature.

## Roadmap / explicitly not done

- No automated test exercises the seed script's idempotency directly (it's a top-to-bottom `main()`
  script, not structured as importable, independently testable functions) — idempotency is proven
  by live, repeated runs against a real database (documented above), not a unit test.
- The demo kit does not cover QR-code scanning specifically (only the ID/PIN-lookup path the QR
  encodes) — scanning the actual printed QR image requires a camera/device, out of scope for an
  automated or scripted proof.
